# Brief Q1 (Sonnet, effort high): stabilkan e2e yang flaky di bawah beban paralel

Masalah: run e2e penuh (2 worker, 4 CPU) gagal 1 test berbeda tiap run, lalu lolos 10/10 saat diulang terpisah. Contoh yang tercatat:
- `tests/e2e/r3b-quran.spec.ts:76` badge Bacaan Jumat (`setDemoTime`)
- `tests/e2e/r3b-quran.spec.ts:29` reader tanpa teks dataset (blok chunk)
- `tests/e2e/r3b-quran.spec.ts:57`
- `tests/e2e/r3b-settings.spec.ts:20` target tidur kembali 22:00 setelah reload (simpan lalu reload)
- `tests/e2e/r3a-devices.spec.ts:121`
- `tests/e2e/s3-a11y` dark mobile `/worship/dhikr/[id]` document-title

## Tugas
1. Reproduksi: jalankan suite penuh `pnpm test:e2e --trace off --repeat-each=3` (atau subset per spec dengan `--workers=4`) untuk memancing flake. Catat setiap kegagalan dan pesannya.
2. Temukan akar masalah, bukan menambah `waitForTimeout`. Pola yang dicurigai: (a) aksi sebelum hidrasi/state tersimpan selesai (tunggu sinyal nyata: teks konfirmasi, `aria-busy=false`, respons IndexedDB); (b) `setDemoTime` tanpa menunggu UI memakai jam baru; (c) seed auth/IndexedDB balapan dengan instance provider; (d) penyimpanan settings yang debounce lalu reload terlalu cepat (perbaiki di kode jika data benar-benar bisa hilang saat user reload cepat).
3. Jika akar masalah ada di kode aplikasi (data hilang saat reload cepat, race di provider), perbaiki kodenya. Itu bug nyata untuk user.
4. Jangan menambah `retries` lokal, jangan skip/hapus test, jangan menaikkan timeout global sebagai solusi.
5. Bukti: `pnpm test:e2e --trace off --repeat-each=3` lolos 0 failed (jika terlalu lama, minimal 3 run penuh berturut-turut 0 failed), tulis angka asli di `docs/sessions/Q1.md`.
